### A5. Is the sandbox real?

Yes — enforced, not just declared.

- The signed entitlements include `com.apple.security.app-sandbox`.
- `containermanagerd` compiled a **25,387-byte `SandboxProfileData`** for signing identifier `com.pibulus.talktype`, whose validation info lists exactly `app-sandbox`, `device.audio-input`, `network.client`.
- Two separate preference stores exist — `~/Library/Containers/com.pibulus.talktype/Data/Library/Preferences/com.pibulus.talktype.plist` (sandboxed) and `~/Library/Preferences/com.pibulus.talktype.plist` (direct) — which proves redirection is active.
- Runtime: app launched, stayed alive 15 s, **0 sandbox denials**, TCC granted for Microphone and Speech Recognition, pasteboard service reachable.

**Gap:** a cross-process `sandbox_check()` probe returns `-1` even for Finder, so it proves nothing. Actual audio capture and the Deepgram socket under sandbox need a human with a microphone.

### A6. Privacy manifest vs actual API use

| Required-reason API | Used? | Declared in HEAD? |
|---|---|---|
| `NSPrivacyAccessedAPICategorySystemBootTime` (`systemUptime`) | **yes** — 7 call sites (`TalkType.swift:2555, 2558, 2717, 2786, 2990, 3257, 3319`) | yes, `35F9.1` (`PrivacyInfo.xcprivacy:17-21`) |
| `NSPrivacyAccessedAPICategoryUserDefaults` | yes, throughout | yes, `CA92.1` |
| File timestamps | no | n/a |
| Disk space | no | n/a |
| Active keyboards | no (`TISCopyCurrentKeyboardInputSource` is not a required-reason API) | n/a |

**The suspicion in the brief is confirmed — but in the shipped binary, not in HEAD.** The DMG currently on `talktype.app/downloads/` (built Oct 15) declares only UserDefaults while its binary calls `systemUptime` three times. HEAD fixes it; the download does not have the fix.

`35F9.1` is the correct reason code (measuring elapsed time between events inside the app).

### A7. Privacy nutrition label

**Recommended answer: "Data Not Collected."**

Defensible because nothing reaches you: Apple speech runs on-device; Deepgram receives audio and Gemini receives transcript text **with the user's own key**; history is local; there is no telemetry, no account, no identifier, no tracking SDK (verified: the binary links only Apple frameworks and contains no Sparkle/analytics).

Arguable because a reviewer sees "microphone audio → `api.deepgram.com`" and may apply the "third-party service acting on your behalf" test.

Put one sentence in the review notes: *cloud engines are opt-in, use the user's own provider account, and stay off until a key is entered.*

## What could not be verified

- **`altool --validate-app` and a full notarization round-trip** — both upload to Apple. Indirect proof only: `notarytool history` authenticates (recent entries `Accepted`), and the Oct 27 DMG validates, staples and is `accepted / source=Notarized Developer ID`.
- **Whether a provisioning profile is mandatory for a sandboxed `Apple Distribution` app.** Evidence points both ways: real App Store apps here mostly carry `com.apple.application-identifier` (Folder Peek, Magnet, Soulver — normally supplied by a profile), but Hidden Bar has only sandbox entitlements and no profile. Xcode always embeds one. Unresolved by design; the cheap move is to embed one.
- **Real dictation under sandbox** — needs a human and a microphone.
- **Per-process sandbox enforcement** — `sandbox_check()` returns `-1` cross-process even for Finder, so that probe is inconclusive. The compiled-profile evidence stands.
- **App Store Connect state** — the API key `AuthKey_YQJMXS475J.p8` exists but no issuer UUID is on disk.

## What this audit touched

Nothing in the real checkout. All builds ran in `rsync` copies under the session temp directory; `build/` and `dist/` in the repo are byte-identical to how they were found (Oct 27), and `git status` was clean at the end.

One methodology correction worth recording: `build.sh` deletes `build/` and `dist/` at the start of every run, so running the two lanes back-to-back in one directory means the second run destroys the first's artifacts. My first sandbox run and string checks accidentally hit the *direct* binary for this reason. Every MAS claim above was re-run against a build confirmed to carry `com.apple.security.app-sandbox` and the MAS-only string table.
